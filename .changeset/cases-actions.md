Model the Cases actions (tasks/D06). `CreateCase` (Cases block, Create case: a `template` that is a `casetemplate` reference, `fields` keyed by Cases system field ids such as `summary` or by `casefield` references for a domain's own fields, written as computed keys `[Refs.casefield("priority")]`, each value static or a JSONPath, an optional `link` `{ onContactNotLinked, contact? }`, and `next` and the catch-all) writes `LinkContactToCase` as `"true"` or `"false"` and, when it links, `ContactToLink` and the `ContactNotLinked` branch before the catch-all, the order of the console's export. A literal template or field id, which the service accepts, keeps the block generic. `GetCase` (Get case: `lastUpdated`, an optional `customerId`, search `fields` and up to ten `response` fields named the same way, the same `link`, and `onMultipleFound`, `onNoneFound` and the catch-all) writes its branches in the order every published flow does, `ContactNotLinked` first and the catch-all last. `UpdateCase` (Update case: a `caseId`, static or a JSONPath such as `$.Case.case_id`, `fields` named the same way, the same `link`, and `next` and the catch-all). The catalog marks `ContactNotLinked` required when and only when `LinkContactToCase` is `"true"` (its first `requiredWhenValue`), so `error-branches` reports it on a linking block and not otherwise, and `builderErrorsFor` offers it on a linking block only. Each is unrestricted by flow type and channel. The HCL writer and reader take them as the typed `create_case`, `get_case` and `update_case` sub-blocks, writing a `casefield` token in a map key or list item as its reference key (`"casefield:priority" = "high"`) and reading it back, which no published flowascode provider accepts until the release that carries them. The `unknown-actions` passthrough fixture holds `UpdateRoutingCriteria` in place of `UpdateCase`, carrying its queue token. The studio's inspector links the contact from one select, wiring or removing `ContactNotLinked` in the same edit, picks the template, and adds request fields and response fields from the system field list or as `casefield` references. Export names a Cases template and a domain's own fields by their bare ids, the form flows hold, at the catalog's `casetemplate` and `casefield` paths only: the inventory's Cases fields carry ListFields' `namespace`, a system field stays literal, and a resource map bound to ids (an awscc `template_id` or `field_id`) names them again on the offline round trip. `flow-cli export` and `diff` load `@aws-sdk/client-connectcases`, a new optional peer of the CLI, and read the instance's Cases domain when it is installed. The service has not yet been asked about these types (rule 44 in `conformance/flow-language/actions.md` is probe pending), so their required keys, branches and spellings are the AWS pages' and published flows' reading.
