Model the Cases actions (tasks/D06). `CreateCase` (Cases block, Create case: a `template` that is a `casetemplate` reference, `fields` keyed by Cases system field ids such as `summary` or by `casefield` references for a domain's own fields, written as computed keys `[Refs.casefield("priority")]`, each value static or a JSONPath, an optional `link` `{ onContactNotLinked, contact? }`, and `next` and the catch-all) writes `LinkContactToCase` as `"true"` or `"false"` and, when it links, `ContactToLink` and the `ContactNotLinked` branch before the catch-all, the order of the console's export. A literal template or field id, which the service accepts, keeps the block generic. The catalog marks `ContactNotLinked` required when and only when `LinkContactToCase` is `"true"` (its first `requiredWhenValue`), so `error-branches` reports it on a linking block and not otherwise, and `builderErrorsFor` offers it on a linking block only. It is unrestricted by flow type and channel. The HCL writer and reader take it as the typed `create_case` sub-block, writing a `casefield` token in a map key as its reference key (`"casefield:priority" = "high"`) and reading it back, which no published flowascode provider accepts until the release that carries it. The studio's inspector links the contact from one select, wiring or removing `ContactNotLinked` in the same edit, picks the template, and adds request fields from the system field list or as `casefield` references. The service has not yet been asked about these types (rule 44 in `conformance/flow-language/actions.md` is probe pending), so their required keys, branches and spellings are the AWS pages' and published flows' reading.
