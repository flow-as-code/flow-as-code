Model the outbound actions (tasks/D04). `CheckOutboundCallStatus` (Check call progress) takes `onStatus`, one path for each of `CallAnswered`, `VoicemailBeep`, `VoicemailNoBeep` and `NotDetected` it branches on, written as Equals conditions in that order, and the catch-all, which its NextAction mirrors. It has no parameters, is unrestricted by flow type, and is restricted to the voice channel (the admin guide's block). The HCL writer and reader take it as the typed `check_outbound_call_status` sub-block. No published flowascode provider accepts these sub-blocks until the release that carries them. `CompleteOutboundCall` (Call phone number) takes an optional `callerId`, an E.164 number or a JSONPath written as `CallerId.Number`, and an optional `connectionTimeLimitSeconds` from 1 to 600, written as a decimal string, with `next` and no error branch. It is legal in outbound whisper flows and modules, on the voice channel. A block carrying the page's `VoiceConnector` (a Chime voice connector) stays generic in every view. The HCL writer and reader take it as the typed `complete_outbound_call` sub-block. In the studio, emptying an optional field nested in an object removes the object when nothing else is left in it, so clearing the caller ID removes `CallerId`. The service has not yet been asked about these types (rule 46 in `conformance/flow-language/actions.md` is probe pending), so their required keys, branches and flow types are the AWS pages' reading. They are deployable at most: a live contact needs outbound campaigns or SMS messaging, neither of which the project's sandbox enables.
