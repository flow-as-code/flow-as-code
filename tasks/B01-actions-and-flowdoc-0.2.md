# B01 Action catalog, modeled-set expansion, FlowDoc 0.2, owned layout

Deliverables: `conformance/flow-language/catalog.json` as the machine-readable action contract for every documented type, with `packages/core/src/actions.ts` held to it by test and the catalog-bound lint rules reading it; FlowDoc 0.2 (`view` ref type, `meta.sourceKind`, optional `description`) with a migration and every reader migrating on read; an owned integer layered auto-layout replacing dagre, specified under `conformance/layout/`; the `view` export fix; 21 more modeled action types, one commit per type, each with its catalog entry, actions.md row, builder block, verified inverter, inspector and palette entries, schema constraints, and fixtures.
Acceptance: every table in actions.ts equals the catalog and the check is proven able to fail; every conformance fixture reads `flowdoc: "0.2"` and a 0.1 document migrates on every read path; `conformance/layout` cases pass and no golden carries dagre output; the stock after-contact-work flow exports; `synth(codegen(doc))` round-trips for every new type's fixture; lint plus the full suite green in CI.

## Assumptions

- The four category pages of the Connect Developer Guide are the authority on which action types exist; recounted on 2026-09-11 at 56 (27 contact, 6 participant, 15 flow control, 8 interactions).
- For the fourteen types modeled before this task, the catalog records exactly what actions.md and the builder already do; nothing about their lint behaviour changes, and the existing conformance/lint fixtures are the proof.
- The in-package copy of the catalog is refreshed by `npm run sync:schema` and lives under `packages/core/src/` because the lint rules that read it run in the studio's worker, where nothing may read the filesystem.

## Notes (2026-09-11, B01e)

- Each type lands in its own commit with the same set of surfaces: the catalog entry (both copies), the actions.md row, reference table entry, constraint and parameter shape, the actions.ts facts held by catalog.test.ts and actions.test.ts, the block class, the inverter with its codegen tests, the schema's per-type constraints, the studio inspector and palette entries, `conformance/roundtrip/contact-routing` and the lint fixtures the type affects. The group's fixture is a module, because no single flow type admits all five actions: queue-to-queue transfer is customer-queue only and transfer to agent is transfer-flow only.
- `DequeueContactAndTransferToQueue`: the page's "not supported in any other type of flow" names flow types, and a module has none, so MODULE stays under the convention recorded above `IN_MODULE` in actions.ts; the research verifier read the sentence as excluding modules and the reading here is recorded so it can be revisited. `NextAction` is required as a modeling choice matching `TransferContactToQueue`; the admin guide's sample for this action shows an empty `NextAction` and its branches section names two branches, so a console export should confirm it. The block accepts a queue, an agent queue, or neither, which the class writes as `{}`; both are `[Optional]` on the page and it does not say where the contact goes with neither, so the destination is recorded as undocumented rather than inferred from `CreateCallbackContact`, whose page does state a TargetQueue fallback.
- `TransferContactToAgent`: terminal, with no parameters and no errors on the page, so it joins `TERMINAL_ACTIONS` and the terminal-blocks rule accepts a transfer flow that ends in it. The page's "in only transfer to agent and transfer to queue flows" is read as the other exclusive restrictions are: MODULE stays.
- `UpdateContactRoutingBehavior`: results and errors are both "None", the first modeled non-terminal action with no error branch. `WITHOUT_CATCH_ALL` in actions.ts records that, `catalogProblems` now derives the expected builder and required errors from it instead of assuming a catch-all (with a mutation test that adds one), the studio stops offering an error handle for such a type (`offersErrorBranch`), and number fields gained `optional` and `clears` so the two mutually exclusive integers can be edited without leaving both set. The 2^63-1 ceiling from the admin guide is not a JSON number JavaScript can carry, so the catalog and the builder record only the floor of 1. Both values are decimal strings on the wire: the console's export of the Sample queue configurations flow writes `"QueuePriority": "1"` and `"QueueTimeAdjustmentSeconds": "600"`, so the kind is `integerString`, as `GetParticipantInput.InputTimeLimitSeconds` already was (found in review, 2026-09-11). Its studio test exposed a gap older than the type: a block inserted from the palette and wired by drags carried `{ NextAction, Errors }` with no `Conditions`, so codegen's byte comparison never matched a block class and the block stayed generic until a save and re-synth wrote the arrays back. Mutations now write an edited action's transitions in synth normal form, and a wired palette block is typed at once.
- `CreateCallbackContact`: the console emits it from the Transfer to queue block's callback tab, not from the Set callback number block the action page links; the row in actions.md says so. The three integers have no JSON example on any page; the console's export of the Sample interruptible queue flow with callback spells them `"5"`, `"1"`, `"600"`, so they are `integerString` (found in review, 2026-09-11; the export also shows `NextAction` on its own target, confirming `next: required`). `CallerId` is a claimed phone number, not a reference type, so it is a plain string the schema does not constrain. The studio's starting values (60 s, 1 attempt, 600 s) are the studio's, inside the page's bounds; the admin guide states no console defaults.
- `UpdateContactCallbackNumber`: two named errors and no catch-all, so it joins `WITHOUT_CATCH_ALL` and both are required; the page does not say either is required, and the reading is that a number the instance cannot dial with nowhere to go is the failure the rule exists to catch. `conformance/roundtrip/unknown-actions` still carries one with an undocumented `Routing` parameter and a `NoMatchingError`, which the inverter refuses, so the fixture's passthrough guarantee holds until B01h re-authors it with an unmodeled type; a codegen test pins that.
- A review of the five commits (eight reviewers, one refuter per finding) confirmed fourteen findings, all applied in one commit: the string spelling above, a Dequeue destination the page never states (reworded at five sites), a misquoted admin guide sentence, the transfer-to-agent channel table the admin guide contradicts itself on, the studio's queue picker erasing an authored agent queue on "(not set)" (clears now apply only on a set), a refused number edit that reached no one (the field now shows the guard's message), the callback block's error order held to `EXTRA_ERRORS` by test, the catalog's integer bounds held to the actions.ts constants by test, and a test for the optional text field. Console exports of every AWS sample flow were read for the string evidence; they also show `InvokeLambdaFunction.InvocationTimeLimitSeconds` as `"4"` and an `UpdateContactRecordingBehavior` with `RecordedParticipants: []` and no error branch, two pre-Phase-B shapes the builder does not write and the schema (for the first) rejects, left for a follow-up.
- Two observations from the recorded exports under `conformance/export/omitted-parameters` (real default flows): the console orders `TransferContactToQueue`'s errors `NoMatchingError` then `QueueAtCapacity`, the reverse of the builder's, so an exported default queue transfer stays a GenericBlock; and `CheckHoursOfOperation`'s exported `NextAction` mirrors the `NoMatchingError` target where the builder mirrors the out-of-hours condition. Both predate Phase B and are left as they are; a later change to match the console's spelling would regenerate the demo goldens.

## Notes (2026-09-11, B01f)

- The sandbox account had no session available during this work, so no wire shape was confirmed live. The recorded exports of the default queue transfer and Sample AB test flows stand in where they can: `DistributeByPercentage` and `CheckMetricData` shapes below are taken from them; `Loop`, `Wait`, `UpdateFlowAttributes` and `GetMetricData` follow their pages and say so.
- `Loop`: no errors on the page, so it joins `WITHOUT_CATCH_ALL`; its two results are fixed conditions and `NextAction` mirrors the done path (`mirrors:condition:DoneLooping`), which a console export should confirm. `LoopCount` is the first `dynamic` parameter: the catalog kind is the static form and the schema accepts a JSONPath too. In the studio, fixed-condition types are now authorable by drags (each drag from the primary handle wires the next unwired operand) and NextAction mirroring is read from the catalog for every type, replacing the `GetParticipantInput` special case; `CheckHoursOfOperation` benefits at once.
- `Wait`: the page puts the catch-all before `ParticipantNotFound`, so `EXTRA_ERRORS` may now name the catch-all to fix its position and `catalogProblems` honours that. `ParticipantNotFound` is the builder's but not required, because the page ties it to one event; the class requires `onParticipantNotFound` exactly when `BotParticipantDisconnected` is waited for and the inverter refuses the unpaired shapes. `NextAction` mirrors the catch-all on the strength of the console pattern in the recorded exports, not the page. The console's other Wait forms (participant type, Lambda and case events, Continue) have no documented keys and stay generic. Corrected after the B01e review turned up console exports of the AWS sample flows: the console writes the timeout as `TimeLimitSeconds` (a decimal string), not the page's `TimeoutSeconds`, and its Sample disconnect flow shows the rest of the shape as modeled (WaitCompleted first, one condition per event, `NextAction` mirroring the catch-all).
- `DistributeByPercentage`: the shape is the console's, read off the recorded Sample AB test export (thresholds `"4"`, `"10"`, `"18"` for 3%, 6%, 8%; `NextAction` mirroring `NoMatchingCondition`; no `Parameters` key, which export normalizes to `{}`). The builder takes percentages and computes the thresholds, so the branches may claim at most 99% and the remainder branch is required. `CONDITION_CATCH_ALL` in actions.ts now names the two types whose catch-all is `NoMatchingCondition`, replacing the `Compare` special case in `catalogProblems`. In the studio a drag claims the next 1% rather than the empty placeholder, which would have demoted the block.
- `UpdateFlowAttributes`: the page's parameter block is malformed and never defines the FlowAttribute value, so the catalog kind is `json` and the builder passes the object through; the plan called for exactly this until a console export confirms the shape. No errors on the page, so it joins `WITHOUT_CATCH_ALL`; the admin guide's over-32-KB Error branch has no type to wire.
- `CheckMetricData`: the recorded default queue transfer export is the evidence for the console's shape: errors `NoMatchingError` then `NoMatchingCondition` (so `EXTRA_ERRORS` names the catch-all first), `NoMatchingCondition` wired on an agent metric although the page limits it to the queue metrics, and `NextAction` mirroring the catch-all. `NoMatchingCondition` is the builder's but not required, because the page says it is not always supported. The builder enforces the page's rule that an agent metric takes exactly `NumberGreaterThan 0`. With that shape the recorded default queue transfer's staffing check now inverts to the typed class, so `conformance/export/omitted-parameters/expected/default-queue-transfer.flow.ts` regenerated once.
- `GetMetricData`: follows its page; no sample flow carries one. `QueueChannel` is the second `dynamic` enum: the schema accepts the two names or a JSONPath, and the studio offers the names. With that the flow-control group is complete and `FLOW_TYPE_UNRESTRICTED` grew by four (Loop, Wait, UpdateFlowAttributes, GetMetricData).
